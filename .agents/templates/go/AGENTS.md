# Go (Golang) 协作规范与 AI Agent 行为准则

本规范基于全局通用协作基准，针对 **Go (Go 1.22+)** 现代技术栈进行了工程特化扩展。下游 Go 项目在引入 AI 辅助研发时，须同时遵守第 1~7 章通用基准与第 8 章技术栈特化规约。

---

## 1. 交互与交付规范 (Interaction & Delivery)

- **语言与表达规范 (Language & Localization)**：
  - 需求沟通、技术方案、代码文档注释、工单任务卡片及评审汇报统一使用清晰地道的中文字符；
  - 系统命令、源码标识符（变量名、函数名、类型名）、专有名词、第三方依赖库名称与报错原始堆栈一律保持原始英文，严禁生硬机翻。
- **文件优先交付 (File-First Delivery)**：
  - **落盘门槛**：结构化交付物（架构设计方案、技术调研、API 接口契约、数据结构定义等）及超过 50 行的新建源码，一律优先直接写入项目对应路径的文件中，严禁在交互会话中倾泻长文本；
  - **即时交互豁免**：原理机制解答、排错推演过程等上下文即时交互内容直接在会话中展开；若用户显式要求“在聊天框展示/无需落盘”，则遵循即时指令。
- **会话反馈与链接呈现 (Session Feedback & Links)**：
  - **微片段限额**：会话向用户汇报时仅提炼核心结论与提纲；新建源码仅展示对外导出的核心公共接口摘要（≤ 15 行）；局部修改仅展示核心变更锚点（≤ 15 行），严禁在交互界面刷屏输出大段未裁剪代码；
  - **会话直达链接**：会话向用户汇报文件变更时统一提供 `[文件相对路径/基名](file:///绝对路径)` 点击直达链接；Windows 路径**必须将反斜杠 `\` 转换为正斜杠 `/`**，严禁在会话中暴露裸露的长路径；
  - **交付正文零绝对路径**：严禁将 `file:///` 或包含本地盘符（如 `C:/`、`D:/`）的绝对路径写入任何 Markdown 交付物正文；文档间互链 100% 采用相对路径（`./`、`../`），外部信源采用标准 HTTPS URL。
- **本地验证闭环与测试防作弊 (Pre-delivery Verification & Test Integrity)**：
  - **严禁未经验证宣称完成**：代码新增或修改完成后，必须在本地终端以无头非交互模式运行项目的标准检查命令（如 `go test ./...`、`golangci-lint run`），验证 100% 成功通过后方可进入交付汇报；
  - **缺陷闭环不甩锅**：若编译报错或测试断言失败，排查与修复是当前任务不可分割的一部分，严禁将未解决的错误直接抛还给用户；
  - **严禁弱化存量测试**：除非当前任务明确声明为既有业务契约的破坏性重构，**严禁为了迎合新代码而私自删除、弱化、注释或断言降级既有存量单元测试**；
  - **真实断言有效性**：新增测试必须覆盖关键业务边界与异常分支，必须包含严谨明确的结果断言，严禁编写无实质断言、纯空跑或滥用全 Mock 糊弄覆盖率的假测试。
- **跨平台一致性与编码标准 (Cross-Platform & Encoding Standards)**：
  - **代码内零硬编码操作系统分隔符**：源码、配置文件与脚本中处理文件路径，一律使用标准正斜杠 `/` 或目标语言标准库提供的路径拼接函数（如 `path/filepath.Join`），严禁在代码或字符串拼接中硬编码宿主机反斜杠 `\`；
  - **文本编码与换行符**：新建源码、配置文件、脚本与文档一律采用 UTF-8 编码（无 BOM），换行符统一使用 Unix LF，防止破坏 Linux CI 与容器运行环境。
- **最小影响面原则 (Minimal Blast Radius)**：
  - 代码改动必须严格聚焦于当前指令与目标缺陷；
  - **严禁对无关源码进行大面积重新格式化、缩进重排或无意义的字符变动**，确保版本控制 Diff 干净、清晰、高可读。
- **幂等性与可重入保证 (Idempotency Invariant)**：
  - AI Agent 编写的任何自动化脚本、环境配置逻辑或批量数据流转操作，**必须具备天然的幂等性**（即无论执行 1 次还是连续执行 N 次，系统最终状态完全一致，绝不产生副作用叠加或状态冲突）。

## 2. 代码与文档注释规范 (Code & Comments)

- **顶层架构与文件注释 (Module & File Doc Comments)**：
  - **单一职责陈述**：新建源文件必须包含遵循 Go Doc 规范的顶层包注释或首函数注释，首段直接清晰陈述该包或结构体的核心职责与架构意图（严禁添加 `职责说明：`、`功能：` 等冗余前缀）；
  - **署名与版本解耦**：代码变更历史、创建者与时间追溯**一律以版本控制系统（Git Commit / Blame）为权威单一信源**；通用基线严禁在文件头强制填充伪作者或时间元数据标签；既有存量文件修改时严格保留原注释。
- **公共契约与行为注释 (Public API Contracts)**：
  - **核心边界说明**：所有对外导出的公共标识符（大写首字母的函数、方法、接口、结构体），必须编写清晰的 Go Doc 文档注释（以标识符名称开头）；
  - **信息增量**：重点说明调用前置条件、并发安全保证、入参空值行为、返回值语义以及可能返回的哨兵错误；自解释的私有小函数免除冗余注释。
- **主干流程与编排注释 (Flow & Steps)**：
  - **关键动作编排**：仅在包含 2 个及以上关键动作 (≥ 2) 的复杂业务流程编排中，采用提纲化步骤标注（如 `// 1. ...`、`// 2. ...`）；**严禁出现仅有单个孤立步骤号的伪步骤**；
  - **提炼自解释单元**：简单流转或透传逻辑无需步骤标注；复杂逻辑应优先提炼为命名清晰的私有辅助函数，避免超长面条代码。
- **清洁代码红线 (Clean Code)**：
  - **命名即文档**：优先通过严谨自解释的命名与常量表达语义，**严禁使用注释为硬编码或魔法值打补丁**；
  - **意图与防御性说明**：行内注释聚焦说明“为什么这么做”与并发/事务防御决策；修改代码时同步修正或清理失效注释；
  - **待办闭环**：严禁随手留空；外部依赖未就绪确需留待办时，统一规范为 `// TODO(<责任人/标识>): <原因与后续动作>`。

## 3. 代码质量与工程健壮性 (Code Quality & Robustness)

- **空安全与前置防御契约 (Null-Safety & Nil Defense)**：
  - **容器查询零空引用**：凡查询或返回一组数据的接口（切片 `[]T`、映射 `map[K]V`），无匹配数据时**统一返回非 nil 的空切片或空 map，严禁返回 nil 切片/nil map**；
  - **可空标量前置防卫**：任何指针、接口或可能为 nil 的对象引用，在调用其字段、方法或解引用前，**必须立即通过前置卫语句显式判空（`if ptr == nil`）**，严禁在未作防卫的情况下直接解引用导致 panic。
- **并发安全与无状态设计 (Concurrency & Statelessness)**：
  - **公共服务保持无状态**：公共 Service、Handler 与单例组件不得持有与特定请求绑定的可变业务状态；
  - **共享可变状态受管与同步**：严禁随意使用未加同步原语（如 `sync.Mutex`、`sync.RWMutex`、`sync/atomic`、并发安全 channel）的全局变量；多并发访问共享资源必须保证协程安全并通过 `-race` 竞态检测验证，彻底杜绝数据竞态（Data Race）。
- **错误与异常处理闭环 (Error & Exception Invariants)**：
  - **零静默吞没**：严禁忽略或吞没任何错误返回值（**绝对禁止 `_ = resp.Body.Close()` 或忽视 `err`**）；所有错误必须显式处理、记录或向上传递；
  - **杜绝日志风暴**：遵循“**要么本地降级并受管记录，要么转化为上层可理解的错误返回**”原则；严禁在同一错误处理分支中既打印堆栈日志又原样返回错误给上层，避免重复刷屏；
  - **受管日志门面**：**严禁在生产源码中使用原始标准输出（裸 `println` / `fmt.Println`）**；必须通过工程配置的受管日志组件（如 `log/slog`、`zap`）进行结构化输出；严禁在交付代码中遗留调试桩。
- **边界解耦与单一职责 (Architectural Decoupling)**：
  - **协议接入层薄层**：负责外部输入（如 HTTP 处理、gRPC Server、CLI 命令）的接入层只负责参数绑定校验与服务调度，**严禁堆积重度领域逻辑，严禁越级穿透直接操作底层私有存储**；
  - **协议接口与内部模型隔离**：对外暴露的 API 契约模型与内部持久层模型必须保持隔离解耦；
  - **杜绝巨石文件**：单个源文件必须保持高内聚与单一关注点，严禁编写大而全的超级模块；维护存量大型文件时严格服从增量外拆原则，新增复杂逻辑独立建模块并在原文件做轻量引用。
- **性能底线与资源安全 (Performance & Resource Safety)**：
  - **杜绝批量低效操作**：严禁在循环体内频繁发起独立的 I/O 读取、数据库查询或外部网络请求；批量操作必须采用批量接口；
  - **资源可靠释放**：涉及文件句柄、网络连接、数据库连接等系统资源的申请，必须使用 `defer` 确保在任何异常路径下都能可靠释放；
  - **依赖克制与锁文件卫生**：严禁未经确认私自引入外部第三方依赖；调整或新增依赖必须维护项目的 `go.mod` 与 `go.sum`，严禁破坏确定性构建环境。

## 4. Git 提交与版本管理 (Git Conventions)

- **显式两级授权 (Explicit Triggers)**：
  - **本地提交**：仅当用户明确发出“提交/commit/保存变更”指令时方可触发，代码改动默认停留在本地工作区供审阅，严禁自主静默提交；
  - **远程推送**：仅当用户明确发出“推送/push/发布到远端”指令时方可操作。
- **精准路径暂存 (Safe Path Staging)**：
  - 暂存代码必须显式指定目标文件路径（`git add <file-path>`）；**严禁使用 `git add .` 或 `-A` 等通配符一网打尽**。
- **规范化提交 (Conventional Commits)**：
  - **格式约束**：统一遵循 Conventional Commits：`<type>(<scope>): <清晰中文描述>`；
  - **多项改动清单**：单次提交包含多个独立模块或功能点时，在提交正文中分行逐项清晰罗列；
  - **工单闭环标准**：使用符合 RFC 5147 规范的 Git Trailer 关联或闭环工单（如 `Closes #12`、`Refs #14`）；
  - **工程门面优先**：若项目工具链中已提供专门的提交门面脚本，优先通过该脚本进行演练与提交。
- **特性即文档准则 (Doc-as-Feature & Atomic Delivery)**：
  - **原子交付**：新功能开发、对外协议变更与配置改造，必须在同一分支与提交中同步交付对应的测试用例与技术文档；
  - **三板斧验收标准**：
    1. **场景痛点**：一句话阐明解决的业务或工程问题；
    2. **最小用例**：提供复制即用的最小配置、命令或示例代码；
    3. **预期呈现**：明确给出调用输出、响应或预期数据形态。

## 5. 工具链执行策略与安全防护 (Toolchain Strategy & Safeguards)

- **环境优先序 (Environment Precedence)**：工具链优先依赖系统 `PATH` 及项目 `go.mod` 所声明的 Go 官方工具与版本执行；严禁猜测或执行非标准路径命令。
- **非交互与无阻塞执行 (Non-Interactive & Headless First)**：
  - **静默批处理参数**：执行命令行任务必须显式附加静默、非交互或自动确认参数；
  - **严禁终端挂起**：严禁执行会挂起等待标准输入（stdin）、键盘按键确认或调用交互式编辑器/分页器的命令；
  - **主动交接阻塞**：若目标命令无法通过参数跳过交互式认证或操作，严禁在后台盲目执行导致挂起；必须主动向用户说明阻塞原因并提供完整命令，引导用户在宿主终端手动执行后继续。
- **破坏性操作熔断红线 (Destructive Action Circuit Breaker)**：
  - **绝对禁止未授权破坏**：严禁在未获得用户明确二次确认的情况下，执行任何不可逆的破坏性命令（包括但不限于 `git reset --hard`、`git clean -f`、强推远端分支、递归清理非临时工作目录、清空持久化存储或无差别强杀系统进程）；
  - **风险前置告警**：遇到确需破坏性重置的场景，必须向用户详尽阐明数据丢失风险，由用户决策并在终端手动执行。

## 6. 信息安全与机密脱敏红线 (Zero-Secret Invariant)

- **零明文不变量 (Zero-Secret Invariant)**：
  - **大写语义占位符**：在任何源码、配置文件、技术文档、脚本及交互会话中，凭据字段统一使用大写语义占位符（如 `YOUR_API_TOKEN`、`user@example.com`）或系统环境变量表达式（如 `${DATABASE_PASSWORD}`、`${API_KEY}`）；
  - **严禁任何形式的机密硬编码**：涵盖数据库账号密码、公有云/第三方平台密钥（Access Key/Secret）、鉴权令牌（Token/JWT）、私钥证书（RSA/SSH）及个人隐私敏感数据。
- **探查资产正向脱敏 (Inspection Sanitization)**：
  - 读取本地运行环境（系统变量、配置文件、本地私有存储）发现真实凭据或内部私网地址时，输出至会话或交付文档前必须强制转译为通用脱敏占位符，严禁原样带出。
- **测试夹具语义化桩豁免 (Mock Exemption)**：
  - 自动化测试与测试夹具中，仅允许使用明显无安全价值的语义化桩数据（如 `test-token`、`dummy-pass`）；严禁在单测中混入真实生产级凭据或有效网络资产。
- **瞬态内存沙箱防护 (Transient Memory Sandbox)**：
  - 用户在会话中主动提供的临时有效凭据，仅限在当前易失性内存中受控调用；会话回复中必须自动掩码（如 `sk-***abcd`）；严禁持久化落盘到任何文件。

## 7. AI 交付前自检清单 (Pre-flight Self-Check Checklist)

在正式向用户宣告交付或提交通知前，AI Agent 必须在会话心智中自检以下项目是否 100% 闭环：

- [ ] **两级授权与安全暂存**：所有代码变更是否在已授权范围？暂存是否显式指定目标文件且彻底杜绝了 `git add .` / `-A`？
- [ ] **本地验证真实闭环**：是否已在本地实际执行过 `go test ./...` 且无报错？并发场景是否通过了 `-race` 竞态检测？
- [ ] **测试真实有效性**：是否 100% 保留且未弱化任何既有存量单测断言？新增测试是否包含严谨有约束力的真实断言（杜绝空跑/假测试）？
- [ ] **并发与状态安全**：公共服务是否保持无状态？全局或共享可变状态是否已通过同步原语提供完整并发安全保护？
- [ ] **破坏性操作零触发**：是否绝对没有擅自执行任何可能造成本地未暂存代码丢失或历史被覆写的破坏性命令？
- [ ] **跨平台与文件编码**：源码中路径处理是否零硬编码反斜杠 `\`（统一采用 `path/filepath`）？新建文件是否遵循 UTF-8 无 BOM 与 LF 换行符？
- [ ] **空安全与边界拦截**：切片/映射结果无匹配时是否均返回了空容器而非 nil？可空指针在解引用前是否均有前置判空？
- [ ] **错误闭环与日志纯净**：是否存在任何忽略错误返回值（`_ = ...`）的隐患？是否排除了裸打印（`fmt.Println`）并杜绝了重复日志风暴？
- [ ] **机密脱敏 100%**：代码、注释、文档与测试中是否绝对没有硬编码任何真实凭据？所有敏感字段是否均使用大写语义占位符？
- [ ] **Diff 纯净与零绝对路径**：Git Diff 是否无大面积无关格式化污染？交付 Markdown 正文中是否做到了 100% 相对路径？
- [ ] **Go 错误链完整性**：透传错误是否均使用了 `fmt.Errorf("...: %w", err)` 包装？错误匹配是否均使用了 `errors.Is()` / `errors.As()`？
- [ ] **Go Goroutine 泄露防御**：启动的 Goroutine 是否均包含基于 `context.Context`、`sync.WaitGroup` 或 Channel 的退出机制？
- [ ] **Go 资源释放前置判空**：`defer resource.Close()` 是否均在确认 `err == nil` 之后立即执行（杜绝空指针解引用崩溃）？

## 8. Go (Go 1.22+) 特化工程规约

### 8.1 Goroutine 生命周期与并发安全
- **杜绝孤儿 Goroutine 泄露**：
  - **绝对禁止启动没有生命周期终结控制的后台 Goroutine**（严禁裸 `go func() { for { ... } }()`）；
  - 启动 Goroutine 必须满足以下条件之一：
    1. 接收外部传入的 `context.Context`，并在主循环中通过 `select { case <-ctx.Done(): return ... }` 监听取消退出；
    2. 使用 `sync.WaitGroup` 或 `golang.org/x/sync/errgroup` 等待并发任务受控收敛；
    3. 接入项目受管的工作协程池（Worker Pool）。
- **并发竞态绝对清零**：
  - 运行单测时必须显式开启竞态检测器（`go test -race ./...`），任何 Data Race 告警均视为致命阻断缺陷；
  - 共享内存访问必须通过 `sync.Mutex`、`sync.RWMutex` 或原子包 `sync/atomic` 保护；复杂状态同步提倡“通过通信来共享内存（Channels）”。

### 8.2 显式错误处理与链式包装
- **零忽略错误原则**：
  - **绝对严禁使用下划线忽略可能返回失败的函数错误**（如 `_ = file.Close()`、`_ = w.Write(b)`）；
  - 必须对每个返回的 `err` 进行显式检查：
    ```go
    if err != nil {
        return fmt.Errorf("failed to process order %s: %w", orderID, err)
    }
    ```
- **现代错误包装与识别**：
  - 跨函数/跨层级向上透传错误时，必须使用 `%w` 动词包装原始错误，保留调用因果链；
  - 判断特定哨兵错误（Sentinel Error）必须使用标准库 `errors.Is(err, ErrNotFound)`；
  - 提取具体错误类型必须使用 `errors.As(err, &targetErr)`，严禁直接使用 `err == ErrNotFound` 进行裸值相等比对。

### 8.3 生产稳健性与 Panic 熔断
- **生产业务代码绝对禁止主动 Panic**：
  - 业务逻辑、RPC 处理器、HTTP Handler 中**绝对严禁主动调用 `panic()`**；
  - `panic` 仅允许出现在应用程序启动引导阶段（如关键配置文件解析失败、无法连接核心注册中心等导致进程无法继续运行的场景）；
- **资源安全与 Defer 顺序防崩溃**：
  - 处理可能返回 `error` 与资源的函数时，**`defer resource.Close()` 必须严格放在确认 `err == nil` 的判断之后**：
    ```go
    // 正确范式：必须先检查 err，再 defer Close
    resp, err := client.Do(req)
    if err != nil {
        return fmt.Errorf("http request failed: %w", err)
    }
    defer resp.Body.Close()
    ```
  - 严禁在检查 `err` 之前执行 `defer resp.Body.Close()`，若请求失败会导致 `resp == nil`，从而引发不可恢复的空指针 panic。

### 8.4 标准项目布局与接口契约
- **标准工程目录结构**：
  - `cmd/`：各可执行主程序的入口点（`main.go`，仅负责依赖装配与启动）；
  - `internal/`：项目的核心业务逻辑代码，由 Go 编译器强制保障私有性，外部仓库无法直接引用；
  - `pkg/`：允许被外部项目导入引用的公共类库；
- **接口设计原则 (Accept Interfaces, Return Structs)**：
  - 函数或方法形参尽量接收最小化的接口（如 `io.Reader`、`io.Closer`），提高可测试性；
  - 构造函数优先返回具体的结构体指针或值，而非抽象接口；
  - 接口定义应当由**调用方（Consumer）定义**，而非实现方在底层预先定义过度抽象的大接口。

### 8.5 现代 Go 1.22+ 范式
- **路由方法匹配**：HTTP 路由优先采用 Go 1.22+ 标准库增强型多路复用器（`http.NewServeMux`），原生支持 HTTP 动词与通配符路径（如 `mux.HandleFunc("GET /api/v1/users/{id}", handleGetUser)`）；
- **循环变量语义安全**：充分利用 Go 1.22 修复的 `for` 循环变量作用域特性，但在闭包引用中仍保持严谨传递参数。

### 8.6 代差排斥清单 (Forbidden Legacy APIs)
- ❌ **绝对禁止使用下划线静默忽略错误**（`_ = fn()`）；
- ❌ **绝对禁止在生产业务流转代码中调用 `panic()`**；
- ❌ **绝对禁止在未检查 `err != nil` 的情况下执行 `defer resp.Body.Close()`**；
- ❌ **绝对禁止在生产代码中使用裸 `fmt.Println` 记录业务日志**（统一使用 `log/slog`）；
- ❌ **绝对禁止启动脱离 Context 或 WaitGroup 管理的无终止条件 Goroutine**。
